# Мәселені талдау: электрондық анықтамалардың түпнұсқалығын тексеру

## 1. Мәселе

Электрондық анықтамалар мен дипломдар көбіне файл, PDF немесе скриншот түрінде жіберіледі. Оны қабылдаған жақ (жұмыс беруші, банк, оқу орны) үш сұраққа жылдам жауап ала алмайды:

1. құжат өзгертілмеген бе (сома, күн, аты-жөні);
2. құжаттың күші жойылмаған ба;
3. құжаттың мерзімі өтпеген бе.

## 2. Қазіргі жағдай (ашық дереккөздер бойынша)

- eGov құжаттарын QR-код немесе қысқа код арқылы ресми тексеру сервисімен тексеруге болады. ЭЦҚ-мен қол қойылған файл үшін қолтаңбаны, қол қоюшының сертификатын және қолтаңбаның құжатқа сәйкестігін тексеру керек.
- eGov Mobile қосымшасында 40 түрлі цифрлық құжат бар. Құжатқа қолжетімділікті үшінші тұлғаға QR-код арқылы беруге болады: кодтың әрекет ету мерзімі 5 минут, оны ұзартуға болады.
- Диплом жағдайында тексерушіге QR-код немесе 6 таңбалы код беріледі.

Яғни ресми жүйеде тексеру құжат иесінің қатысуын немесе ресми сервиске онлайн кіруді талап етеді.

## 3. Жобаның таңдаған мәселесі

Қабылдаушы жаққа тек файлдың өзі келген кезде оның бүтіндігін және күйін тексеретін қарапайым, түсінікті механизмнің моделі керек. Жоба осы механизмді Java тілінде көрсетеді. Бұл ресми жүйенің көшірмесі емес, оқу моделі.

## 4. Шешім

Консольдік Java қосымшасы:

1. **Беруші** құжатты жасайды, оған RSA қолтаңба (SHA256withRSA, стандартты JCA) қояды және құжат нөмірін тізілімге жазады. Нәтиже: `.edoc` файлы.
2. **Тексеруші** `.edoc` файлын ашады. Бағдарлама ретімен тексереді: қолтаңба, тізілімдегі жазба, күшін жою, мерзім.
3. Нәтиже бес күйдің бірі: `VALID`, `TAMPERED`, `NOT_FOUND`, `REVOKED`, `EXPIRED`.
4. Файлдағы бір таңба өзгертілсе де қолтаңба бұзылады, сондықтан жалған құжат `TAMPERED` деп танылады.

## 5. Қатысушылар

| Қатысушы | Рөлі |
|---|---|
| Беруші | құжат жасайды, қол қояды, күшін жояды, тізілімді көреді |
| Иесі (азамат) | файлды алып, тексерушіге көрсетеді (жүйеден тыс) |
| Тексеруші | файлды тексереді, нәтижені көреді |

## 6. Функционалдық талаптар

| № | Талап |
|---|---|
| FR-1 | Төрт түрлі анықтаманы жасау (ЖСН, аты-жөні, мәтін, жарамдылық мерзімі) |
| FR-2 | Құжатқа RSA қолтаңба қою және `.edoc` файлына сақтау |
| FR-3 | Берілген құжаттарды тізілімге жазу (жеке деректерсіз) |
| FR-4 | Файлды тексеру: қолтаңба, тізілім, күшін жою, мерзім |
| FR-5 | Құжаттың күшін жою |
| FR-6 | Тізілімді көрсету және файлға сақтау |
| FR-7 | Демо-сценарий: шығару, тексеру, өзгерту, күшін жою |
| FR-8 | Қате пішімдегі файлды түсінікті хабармен қабылдамау |
| FR-9 | Қатарынан 3 сәтсіз тексеруден кейін тексеруді уақытша бұғаттау |

## 6.1. Қосымша мәселе: сәтсіз тексерулерді қайталау (іріктеп табу)

**Мәселе.** Шабуылдаушы жалған немесе бұзылған `.edoc` файлдарын автоматты түрде қайта-қайта тексеруге жібере алады. Мақсаты: тізілімдегі құжат нөмірлерін іріктеп табу (`NOT_FOUND` пен `TAMPERED` жауаптарының айырмасынан құжаттың бар-жоғын білу) немесе жүйені тексеру сұраулармен шаршату. RSA қолтаңбаны табу мүмкін емес, бірақ шектеусіз әрекет жүйеге ақпарат береді.

**Шешім: уақытша бұғаттау.** Класс `RateLimiter`, `VerificationService` ішінде қолданылады.

| Параметр | Мәні |
|---|---|
| Қатарынан сәтсіз тексеру (`TAMPERED`, `NOT_FOUND`, бұзылған файл) | 3 |
| Бұғаттау уақыты | 5 минут |
| Қайталап бұғаттау | 5 → 10 → 20 минут, ең көбі 60 минут |
| `VALID` нәтиже | санағышты нөлге түсіреді |
| `REVOKED`, `EXPIRED` | шабуыл емес, санаққа кірмейді |

Бұғат кезінде тексеру орындалмай, «қанша секундтан кейін қайталаңыз» хабары шығады. Демо: мәзірдегі 6-тармақ.

**Шектеу.** Консольдік қосымшада тексеруші біреу, сондықтан бұғат кілті тұрақты (`verifier`). Нақты жүйеде кілт IP мекенжай немесе есептік жазба болар еді.

## 7. Қауіпсіздік және шектеулер

- Тізілімде тек ID, құжат түрі, мерзімдер және күй сақталады. Аты-жөні, ЖСН және мәтін тізілімге түспейді.
- Құжат өрістерінің бәрі қолтаңбамен қорғалған, мерзімін ұзарту да `TAMPERED` береді.
- Жабық кілт `keys/` папкасында ашық мәтінмен сақталады және репозиторийге түспейді (`.gitignore`). Нақты жүйеде кілт HSM-де немесе ҰКО-да болар еді.
- Қолтаңба ГОСТ Р 34.10-2015 емес, RSA негізінде жасалады, сертификат тізбегі және CRL/OCSP жоқ.
- Оқу моделінде беруші мен тексеруші бір бағдарламада және бір тізілімді қолданады. Шынайы жүйеде тексеруші беруші жариялаған ашық кілтті және тізілімді желі арқылы алар еді.

## 8. Табыс критерийлері

- Демо-сценарийде `VALID`, `TAMPERED` және `REVOKED` нәтижелері дұрыс шығады.
- JUnit 5 тесттерінің бәрі өтеді (кемінде 10, жобада 50).
- Бағдарлама VS Code-та Maven арқылы және `Run` батырмасымен іске қосылады.
